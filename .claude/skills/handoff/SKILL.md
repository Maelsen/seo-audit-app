# handoff

Lockerer Build-Report fuer Marlin. Drei Sektionen: was gebaut, was verifiziert, ob du selber checken solltest.

## Stil-Regeln (PFLICHT)

Schreib in Marlins eigenem Stil — siehe `feedback_writing_style.md`:

- Umgangssprache, locker, kein Buero-Deutsch
- Keine Metaphern, keine Bindestriche, keine Doppelpunkte am Anfang
- So wie Marlin selbst reden wuerde
- Keine Emojis im Body (haechstens ✓/⚠/✗ als Marker)
- Keine "Generated by Claude" Floskeln

## Output-Format

```
HANDOFF — <feature name in normaler sprache>

WAS GEBAUT WURDE
1-3 saetze in deinem stil. was kann die app jetzt das sie vorher nicht konnte. nicht "implementiert" oder "umgesetzt" sagen — eher "gebaut" / "fertig" / "geht jetzt".

WAS ICH GETESTET HAB
- compile + lint clean
- backend-apis durchgepingt (welche genau)
- editor in chrome durchgeklickt (block-click, drag, save, reload)
- pdf gerendert + gegen vasileios-referenz visuell verglichen
- ggf. weiteres

DAS SOLLTEST DU SELBER CHECKEN
Hier kommt die ehrliche Einschaetzung. Pro Punkt: KURZ warum du das selber besser kannst als ich.

⚠ <Punkt>: <warum hand-test besser>
⚠ <Punkt>: <warum hand-test besser>

oder wenn nichts: "fuer dieses Feature gibt es nichts wo du selber besser bist als ich. screenshot reicht."

DAS BRAUCHST DU NICHT CHECKEN
- <Punkt>: <warum claude das schon abgedeckt hat>
- <Punkt>: <warum>
```

## Heuristik fuer "selber checken vs claude reicht"

### LOHNT SICH HAND-TEST (Marlin selber besser als Claude)

- **Animationen** — wie smooth ist der Transition, ist der Easing-Curve angenehm
- **Hover-States / Click-Feeling** — wirkt der Button responsive oder hat er Latenz
- **Scroll-Smoothness** — ruckelt es, ist die Velocity natuerlich
- **Keyboard-Navigation** — Tab-Order durchklicken, Shortcuts probieren
- **Loading-State-Feeling** — wirkt das Warten zu lang, fehlt ein Skeleton-Loader
- **Mobile-Touch / Gesten** — funktionieren Swipes, fuehlen sich Taps an
- **Sound / Haptic** — wenn relevant
- **Visuelles "stimmt das Branding"** — passt der Vibe, fuehlt es sich nach Artistic Avenue an
- **Micro-Interactions** — small details die ein Screenshot nicht einfaengt
- **Error-Message-Wording aus User-Perspektive** — verstehe ich als Endkunde was hier los ist
- **Mehrere Pages durchklicken im Flow** — fuehlt sich der gesamte User-Journey logisch an

### REICHT WENN CLAUDE TESTET

- Static Layout / Position / Groesse — Screenshot reicht
- Functional correctness (Block existiert, Wert stimmt, Save persistiert) — Claude testet via DOM/API
- API-Responses, Status-Codes, Body-Shape
- Persistenz (Save → Reload → JSON)
- Validation (Schema, required fields)
- Compile / Lint / Type-Safety
- PDF-Output gegen Pixel-Vermessung
- Console-Errors (Claude liest sie)
- Visual-Diff gegen Referenz-PDF
- Edge-Cases mit unterschiedlichen Inputs

### Rule of Thumb

> "Wenn ich es im Screenshot sehen kann, hab ich es. Wenn es darum geht wie es sich anfuehlt, brauchst du dich."

## Beispiele

### Beispiel 1: Feature ist "Page-Chrome" (statisches Layout, M3)

```
DAS SOLLTEST DU SELBER CHECKEN
fuer dieses feature gibt es nichts wo du selber besser bist als ich. das ist statisches layout, screenshot zeigt alles. logo + header-text + footer-stripes wurden pixel-vermessen gegen vasileios. drag funktioniert in der editor-ui (hab ich live durchgeklickt). reicht.

DAS BRAUCHST DU NICHT CHECKEN
- pixel-position (vermessen, <0.3mm drift)
- editor-block-selection (durchgeklickt, inspector zeigt korrekte werte)
- save+reload-persistenz (api-response gepruerft, json hat den drag-wert)
- pdf-output gegen vasileios (pixel-perfect side-by-side)
```

### Beispiel 2: Feature ist "AI-Chat-Floating-Button mit Animation"

```
DAS SOLLTEST DU SELBER CHECKEN
⚠ floating-button-position bei scroll: zoom rein, raus, scrollen — fuehlt es sich nach IntersectionObserver-bug an oder smooth?
⚠ chat-panel slide-in animation: ist der easing-curve nicht zu hart
⚠ message-typing-indicator: wirkt das organisch oder mechanisch
⚠ submit-button-state-change: feedback bei click ausreichend?

DAS BRAUCHST DU NICHT CHECKEN
- chat-api-response (durchgeptcht, schemas validiert)
- tool-call-execution (durchgelaufen mit echtem agent)
- session-persistenz (reload behaelt history)
- error-handling bei rate-limit (mock-test gefahren)
```

## Wann nutzen

Am Ende eines Milestones nach `/verify-feature` gruen. Nicht zwischendurch — der Skill ist fuer den finalen Hand-Off-Moment.

Auch sinnvoll wenn Marlin sagt "wie weit sind wir" oder "was hast du grad gemacht".
